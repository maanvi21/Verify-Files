1. Introduction

In today's digital world, ensuring the integrity and authenticity of files is a critical challenge. Documents, certificates, legal contracts, software releases, and sensitive data are frequently shared across networks — and any unauthorized modification can have serious consequences. Traditional file verification methods rely on centralized authorities, which are vulnerable to single points of failure, data tampering, and trust issues.

This project presents a Decentralized File Hash Verification System built on the Ethereum blockchain. It enables users to register the cryptographic hash (SHA-256) of any file on an immutable, distributed ledger. Later, anyone can verify whether a file has been tampered with by comparing its computed hash against the on-chain record — without relying on any centralized server or authority.

1.1 Problem Statement

Current file integrity verification systems are centralized — a single database stores hash records, making them susceptible to tampering, unauthorized access, and single-point-of-failure risks. There is a need for a decentralized, transparent, and tamper-proof solution that provides publicly verifiable proof of file integrity without requiring trust in a central authority.

1.2 Objectives

  • Design and implement a Solidity smart contract to store and verify file hashes on the Ethereum blockchain.
  • Build a web-based frontend that computes file hashes client-side and interacts with the smart contract via MetaMask.
  • Ensure that registered file hashes are immutable and publicly verifiable.
  • Prevent duplicate registration of the same file hash.
  • Provide a user-friendly interface for non-technical users.
  • Deploy and test the system on a local Ganache blockchain.

1.3 Scope

The system is designed as a proof-of-concept suitable for academic demonstration and local deployment. It supports any file type and size (hashing is performed client-side in the browser). The smart contract is deployed on a local Ganache blockchain but can be deployed to Ethereum testnets (Sepolia, Goerli) or mainnet without code changes.

2. Literature Review & Background

2.1 What is Blockchain?

A blockchain is a distributed, decentralized, and immutable digital ledger that records transactions across a network of computers. Each block contains a cryptographic hash of the previous block, a timestamp, and transaction data — forming an unbreakable chain. Key properties include:

  • Decentralization: No single entity controls the network; all nodes maintain a copy of the ledger.
  • Immutability: Once data is written to a block and confirmed, it cannot be altered or deleted.
  • Transparency: All transactions are publicly visible and auditable by any participant.
  • Consensus: Network participants agree on the state of the ledger through consensus mechanisms (e.g., Proof of Work, Proof of Stake).

2.2 Ethereum & Smart Contracts

Ethereum is a decentralized, open-source blockchain platform that supports smart contracts — self-executing programs stored on the blockchain that automatically enforce rules and conditions without intermediaries. Unlike Bitcoin, which primarily handles value transfer, Ethereum provides a Turing-complete virtual machine (the Ethereum Virtual Machine, or EVM) capable of running arbitrary code.

Smart contracts are written in Solidity, compiled to EVM bytecode, and deployed to the Ethereum network. Once deployed, a smart contract has its own address, stores persistent state, and exposes functions that users can call by sending transactions.

Key Concept: A smart contract is like a vending machine — once deployed, it operates autonomously according to its programmed rules. No one (not even the creator) can alter its code after deployment.

2.3 Cryptographic Hash Functions

A cryptographic hash function is a one-way mathematical function that maps input data of arbitrary size to a fixed-size output (the "hash" or "digest"). SHA-256 (Secure Hash Algorithm 256-bit) is used in this project. Key properties:

Table 2.1 — Properties of Cryptographic Hash Functions
PropertyDescription
DeterministicThe same input always produces the same hash output.
Fixed Output SizeSHA-256 always produces a 256-bit (32-byte) hash, regardless of input size.
Avalanche EffectA tiny change in the input completely changes the output hash.
Pre-image ResistanceGiven a hash, it is computationally infeasible to find the original input.
Collision ResistanceIt is practically impossible to find two different inputs that produce the same hash.

Example: The SHA-256 hash of the string "hello world" is:
b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9

Changing even one character (e.g., "Hello world") produces a completely different hash:
64ec88ca00b268e5ba1a35678a1b5316d212f4f366b2477232534a8aeca37f3c

2.4 Existing Solutions

Several centralized services exist for file hash verification (e.g., VirusTotal, HashCalc), but they rely on trusted servers. Blockchain-based solutions like Proof of Existence (poex.io) and Stampery have demonstrated the concept but often require custom tokens or are no longer maintained. This project provides a simple, self-deployable, open-source alternative.

4.4 Frontend Architecture

The frontend is a single-page HTML application with three main sections:

  • Register Section: File picker → SHA-256 hash computation → blockchain registration.
  • Verify Section: File picker or manual hash input → blockchain lookup → result display.
  • My Files Section: Displays all files registered by the connected wallet address.

The frontend uses the Web Crypto API (crypto.subtle.digest) for client-side SHA-256 hashing — the file never leaves the user's browser. Communication with the smart contract is handled by Web3.js through MetaMask's injected provider.

5. System Design & Implementation

5.1 Smart Contract Design

The smart contract follows a clean, modular design with separation between storage, logic, and access control. The contract is intentionally kept simple and gas-efficient.

5.2 Data Structures

FileRecord Struct

struct FileRecord {
    address owner;       // The address that registered the hash
    string  fileName;    // Human-readable filename
    uint256 timestamp;   // Block timestamp when the hash was stored
    bool    exists;      // Guard flag for existence checks
}

State Variables

mapping(bytes32 => FileRecord) private fileRecords;   // Hash → Record
mapping(address => bytes32[])  private userFiles;      // Address → Hashes[]
uint256 public totalFiles;                              // Counter

Using bytes32 for the file hash is optimal because SHA-256 produces exactly 256 bits (32 bytes), which maps directly to Solidity's bytes32 type — the most gas-efficient way to store a hash on-chain.

5.4 Events & Modifiers

Events

event FileRegistered(
    bytes32 indexed fileHash,    // Indexed for efficient filtering
    address indexed owner,       // Indexed for per-user queries
    string  fileName,
    uint256 timestamp
);

Events are emitted during write operations and stored in transaction logs. They are not stored in contract storage (saving gas) but can be queried by off-chain applications. The indexed keyword enables efficient filtering by hash or owner address.

Modifiers

modifier hashNotRegistered(bytes32 _fileHash) {
    require(!fileRecords[_fileHash].exists, "File hash already registered");
    _;
}

modifier hashExists(bytes32 _fileHash) {
    require(fileRecords[_fileHash].exists, "File hash not found");
    _;
}

5.5 Frontend Implementation

The frontend is a single index.html file with embedded CSS and JavaScript. Key implementation details:

Client-Side File Hashing

async function hashSelectedFile(inputId, displayId) {
    const file   = fileInput.files[0];
    const buffer = await file.arrayBuffer();
    const hashBuffer = await crypto.subtle.digest("SHA-256", buffer);
    const hashArray  = Array.from(new Uint8Array(hashBuffer));
    const hashHex    = "0x" + hashArray
        .map(b => b.toString(16).padStart(2, "0")).join("");
}

The crypto.subtle.digest API is a native browser API that computes SHA-256 hashes entirely on the client side. The file data never leaves the user's machine — only the 32-byte hash is sent to the blockchain.

6. Working of the System

6.1 File Registration Flow

  1. The user opens the frontend and clicks "Connect MetaMask" to link their Ethereum wallet.
  2. The user selects a file using the file picker in the Register section.
  3. The browser reads the file and computes its SHA-256 hash using the Web Crypto API. The file never leaves the user's machine.
  4. The computed hash (32 bytes, displayed as a 0x-prefixed hex string) is shown on screen.
  5. The user enters a filename (auto-filled from the file name) and clicks "Register on Blockchain".
  6. Web3.js constructs a transaction calling registerFile(hash, fileName) and sends it to MetaMask.
  7. MetaMask shows a confirmation popup displaying the gas cost. The user clicks "Confirm".
  8. The signed transaction is sent to Ganache, which mines it instantly.
  9. The smart contract executes:
    • Validates that the hash is not zero and the filename is not empty.
    • Checks that the hash is not already registered (prevents duplicates).
    • Creates a FileRecord in the fileRecords mapping.
    • Appends the hash to the user's userFiles array.
    • Increments totalFiles.
    • Emits the FileRegistered event.
  10. The transaction receipt is returned to the frontend, which displays the transaction hash and block number.

6.2 File Verification Flow

  1. The user selects a file in the Verify section (or pastes a hash manually).
  2. The browser computes the SHA-256 hash of the selected file.
  3. The user clicks "Verify".
  4. Web3.js calls the verifyFile(hash) function — this is a view function, so it costs no gas and requires no MetaMask confirmation.
  5. The smart contract looks up the hash in the fileRecords mapping and returns:
    • isRegistered — whether the hash exists on-chain.
    • owner — the address that registered it.
    • fileName — the stored filename.
    • timestamp — when it was registered.
  6. The frontend displays the result:
    • ✅ Verified: Shows owner address, filename, and registration date.
    • ❌ Not Found: Indicates the file hash was never registered.

8. Security Analysis

Table 8.1 — Security Measures
ThreatMitigation
Hash Tampering Once stored on the blockchain, file hashes are immutable. No one — not even the contract deployer — can modify or delete a registered hash.
Duplicate Registration The hashNotRegistered modifier prevents the same hash from being registered twice, ensuring first-registrant ownership.
Reentrancy Attack The contract does not make external calls or transfer ETH, so reentrancy is not applicable.
Integer Overflow Solidity 0.8.x includes built-in overflow/underflow checks. The totalFiles counter is safe.
Input Validation Zero hashes and empty filenames are rejected with explicit require statements.
Private Key Security Private keys are managed by MetaMask and never exposed to the frontend application.
File Privacy Files are hashed client-side in the browser. The actual file data is never uploaded or transmitted — only the 32-byte hash goes on-chain.
Front-Running On a public network, miners could theoretically front-run a registration. On Ganache (local), this is not a concern. A commit-reveal scheme could mitigate this on mainnet.

10. Advantages & Limitations

10.1 Advantages

  • Tamper-Proof: Once registered, a file hash cannot be altered or deleted by anyone, including the contract owner.
  • Decentralized: No central authority or server is needed. The Ethereum network ensures availability and redundancy.
  • Transparent: All registered hashes and their metadata are publicly auditable on the blockchain.
  • Privacy-Preserving: Only the hash is stored on-chain — the actual file content remains private with the user.
  • Low Cost: Storing a 32-byte hash is one of the cheapest on-chain operations.
  • Universal Verification: Anyone can verify a file's integrity without needing permission from the original uploader.
  • Timestamped: Block timestamps provide a verifiable record of when a file was registered.
  • No File Size Limits: Since only the hash is stored, files of any size can be registered.

10.2 Limitations

  • Not a Proof of Authorship: Registering a hash does not prove the uploader created the file — only that they registered it first.
  • No File Storage: The system only stores hashes, not the actual files. Users must retain their own copies.
  • Gas Costs on Mainnet: Each registration transaction requires gas fees, which vary with network congestion.
  • Irreversibility: Once registered, a hash cannot be removed — this could be a concern for accidental registrations.
  • Scalability: On-chain storage is expensive. For high-volume use cases, a Layer 2 solution would be more practical.
  • Network Dependency: The system requires an Ethereum node (or Ganache) to be running.

11. Future Enhancements

  1. IPFS Integration: Store the actual file on IPFS (InterPlanetary File System) and register the IPFS CID on-chain, combining decentralized storage with on-chain verification.
  2. Ownership Transfer: Allow the original registrant to transfer file ownership to another address.
  3. File Revocation: Add the ability to mark a file registration as "revoked" (without deleting the original record).
  4. Multi-Signature Registration: Require multiple parties to approve a file registration for collaborative workflows.
  5. Layer 2 Deployment: Deploy on Polygon, Arbitrum, or Optimism for lower gas fees and faster confirmation times.
  6. Access Control: Implement role-based access (admin, verifier, registrant) using OpenZeppelin's AccessControl library.
  7. Batch Registration: Support registering multiple file hashes in a single transaction to reduce gas costs.
  8. ENS Integration: Display human-readable names (e.g., "alice.eth") instead of raw Ethereum addresses.
  9. Email/Webhook Notifications: Notify users when their file's hash is verified by someone.
  10. Mobile App: Build a React Native or Flutter mobile application for on-the-go file verification.

12. Conclusion

The Decentralized File Hash Verification System successfully demonstrates how blockchain technology can be applied to solve real-world problems of file integrity and authenticity verification. By leveraging Ethereum smart contracts, the system provides:

  • An immutable, tamper-proof record of file hashes on a decentralized ledger.
  • A transparent verification mechanism that anyone can use without trusting a central authority.
  • A privacy-preserving design where file contents never leave the user's device.
  • A gas-efficient implementation using optimized data types and Solidity best practices.

The project was developed using industry-standard tools — Solidity, Truffle, Ganache, MetaMask, and Web3.js — providing hands-on experience with the complete Ethereum development workflow: writing smart contracts, deploying to a blockchain, running automated tests, and building a Web3 frontend.

While currently deployed on a local Ganache blockchain for development and testing purposes, the system is fully compatible with Ethereum testnets and mainnet, making it a viable foundation for production-grade file verification applications.
